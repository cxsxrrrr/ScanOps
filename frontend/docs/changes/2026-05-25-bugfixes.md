## BUG-001 — Violación de Rules of Hooks (CRÍTICO)

**Severidad:** Crítica  
**Archivo:** `src/App.jsx`  
**Líneas afectadas (antes):** 19–22

### Descripción

React prohíbe llamar hooks dentro de sentencias condicionales (`if`, ternarios, bucles). El hook `useApiSetup` se invocaba dentro de un bloque `if (authEnabled)`:

```jsx
// INCORRECTO — violación de Rules of Hooks
function App({ authEnabled = true }) {
    if (authEnabled) {
        useApiSetup()  // Hook condicional
    }
    ...
}
```

Esto provoca un `Invalid hook call` en React StrictMode (activo por defecto en React 19). En producción, el orden de hooks cambia entre renders si `authEnabled` varía, corrompiendo el estado interno de React.

### Causa raíz

`useApiSetup` usa `useAuth()` de Clerk, que requiere `<ClerkProvider>` en el árbol. Cuando `authEnabled=false`, el `ClerkProvider` no se renderiza, haciendo imposible llamar el hook de forma incondicional en el mismo componente.

### Solución aplicada

Se extrajo la lógica autenticada a un componente separado `AuthenticatedApp`. Los hooks siempre se llaman consistentemente dentro de ese componente; `App` solo hace renderizado condicional:

```jsx
// CORRECTO — hook siempre se llama en el mismo componente
function AuthenticatedApp() {
    useApiSetup()  // Siempre ejecutado, sin condición
    return <>{/* rutas */}</>
}

function App({ authEnabled = true }) {
    if (!authEnabled) return <NoAuthFallback />
    return <AuthenticatedApp />
}
```

### Impacto

- **Antes:** Crash garantizado en React StrictMode; comportamiento indefinido en producción si `authEnabled` cambia.
- **Después:** Cumple Rules of Hooks; comportamiento estable y predecible.

## BUG-002 — XSS via dangerouslySetInnerHTML (CRÍTICO)

**Severidad:** Crítica  
**Archivo:** `src/pages/Report.jsx`  
**Líneas afectadas (antes):** 204–213

### Descripción

El resumen ejecutivo generado por IA se renderizaba directamente como HTML usando `dangerouslySetInnerHTML`, con únicamente transformaciones de strings mediante `.replace()`:

```jsx
// INSEGURO — inyección HTML sin sanitizar
dangerouslySetInnerHTML={{
    __html: report.executive_summary.content
        .replace(/\n/g, '<br>')
        .replace(/## /g, '<h2 class="...">')
        .replace(/\*\*(.*?)\*\*/g, '<strong>$1</strong>')
}}
```

Las transformaciones no eliminan ni escapan etiquetas HTML arbitrarias. Si el campo `content` proveniente del backend contiene `<script>alert(1)</script>` o atributos `onerror=...`, el navegador los ejecuta. Vectores posibles:
- Compromiso del backend
- Respuesta maliciosa de la API de IA
- Ataque man-in-the-middle (sin HTTPS)

### Solución aplicada

Se eliminó `dangerouslySetInnerHTML` completamente. Se implementó la función `renderMarkdown()` que convierte el contenido a elementos React seguros sin ningún HTML crudo:

```jsx
// SEGURO — React escapa automáticamente todo el contenido
function renderMarkdown(content) {
    return content.split('\n').map((line, i) => {
        if (line.startsWith('## ')) {
            return <h2 key={i} className="text-lg font-bold mt-4 mb-2">{line.slice(3)}</h2>
        }
        if (!line.trim()) return <br key={i} />
        const parts = line.split(/(\*\*[^*]+\*\*)/)
        return (
            <p key={i}>
                {parts.map((part, j) =>
                    part.startsWith('**') && part.endsWith('**')
                        ? <strong key={j}>{part.slice(2, -2)}</strong>
                        : part
                )}
            </p>
        )
    })
}
```

React escapa automáticamente cualquier contenido que no sea JSX explícito, eliminando la superficie de ataque XSS.

### Impacto

- **Antes:** Vulnerabilidad XSS. Contenido malicioso del backend podría ejecutar JavaScript arbitrario en el browser del usuario.
- **Después:** Sin superficie de XSS. Toda la cadena de renderizado usa el modelo de seguridad nativo de React.

## BUG-003 — alert() bloqueante reemplazado por UI in-page (IMPORTANTE)

**Severidad:** Importante  
**Archivo:** `src/pages/Report.jsx`  
**Líneas afectadas (antes):** 27, 47

### Descripción

Los errores de carga y descarga de reportes usaban `window.alert()`:

```jsx
// MAL — bloquea el hilo principal, rompe UX
const detail = err?.response?.data?.detail
if (detail) alert(detail)
```

`alert()` bloquea el event loop, no puede estilizarse, y rompe la consistencia visual del sistema de notificaciones del resto de la app.

### Solución aplicada

Se añadieron dos estados de error (`loadError`, `downloadError`) que muestran mensajes inline con el mismo sistema visual (glassmorphism + rojo/AlertCircle) usado en el resto de páginas:

```jsx
const [loadError, setLoadError] = useState(null)
const [downloadError, setDownloadError] = useState(null)

// En handleDownload:
setDownloadError(detail || 'Error al descargar el reporte.')

// En el JSX, junto a los botones de descarga:
{downloadError && (
    <div className="flex items-center gap-2 text-red-400 text-sm bg-red-500/5 border border-red-500/10 px-3 py-2 rounded-lg">
        <AlertCircle className="w-4 h-4 flex-shrink-0" />
        {downloadError}
    </div>
)}
```

### Impacto

- **Antes:** Diálogos nativos del browser, bloqueantes, sin estilo.
- **Después:** Mensajes de error inline, consistentes con el design system.

## BUG-004 — Selector CSS dark mode incorrecto (IMPORTANTE)

**Severidad:** Importante  
**Archivo:** `src/index.css`  
**Línea afectada (antes):** 103

### Descripción

El override de `glass-strong` para dark mode usaba un selector CSS inválido:

```css
/* INCORRECTO — "dark" como elemento HTML, nunca coincide */
dark .glass-strong {
  background: hsl(var(--glass-bg) / 0.10);
}
```

El selector `dark .glass-strong` busca un elemento HTML `<dark>` como ancestro. En realidad, Tailwind aplica dark mode agregando la clase `.dark` al elemento `<html>`, por lo que el selector correcto requiere el punto (`.dark`).

### Solución aplicada

```css
/* CORRECTO */
.dark .glass-strong {
  background: hsl(var(--glass-bg) / 0.10);
}
```

### Impacto

- **Antes:** `glass-strong` no aplicaba su variante dark correctamente. El fondo era demasiado opaco en modo oscuro (usaba el valor por defecto `0.12` en vez del `0.10` diseñado).
- **Después:** Dark mode de `glass-strong` funciona según el diseño.

## BUG-005 — Sin cancelación de requests HTTP al desmontar (IMPORTANTE)

**Severidad:** Importante  
**Archivos afectados:** 9 archivos

| Archivo | Función de carga |
|---------|-----------------|
| `src/pages/Dashboard.jsx` | `loadDashboard()` |
| `src/pages/URLs.jsx` | `loadData()` |
| `src/pages/ScanHistory.jsx` | `loadScans()` |
| `src/pages/Report.jsx` | `loadReport()` |
| `src/pages/Profile.jsx` | `loadProfile()` |
| `src/pages/Settings.jsx` | `loadAll()` |
| `src/pages/Plans.jsx` | `loadOrgData()` |
| `src/pages/admin/AdminDashboard.jsx` | `loadData()` |
| `src/layouts/DashboardLayout.jsx` | `loadProfile()` |

### Descripción

Todos los `useEffect` que disparaban llamadas HTTP carecían de función de limpieza (`cleanup`). Si el usuario navegaba a otra ruta antes de que completara la respuesta, el request continuaba y React intentaba actualizar el estado de un componente ya desmontado:

```jsx
// INCORRECTO — sin cancelación
useEffect(() => {
    loadDashboard()
}, [])
```

Consecuencias:
1. **Requests de red desperdiciados** — el servidor procesa y responde aunque nadie escuche.
2. **Posibles actualizaciones de estado en componentes desmontados** — warnings en desarrollo, comportamiento indefinido en edge cases.
3. **Race conditions** — si el componente se monta/desmonta rápido (Strict Mode monta dos veces), pueden llegar dos respuestas y la segunda sobreescribe la primera con datos obsoletos.

### Solución aplicada

Patrón uniforme en todos los archivos usando `AbortController`:

```jsx
// CORRECTO — con cancelación
useEffect(() => {
    const controller = new AbortController()
    loadDashboard(controller.signal)
    return () => controller.abort()  // cleanup al desmontar
}, [])

async function loadDashboard(signal) {
    try {
        const [urlsRes, scansRes, orgRes] = await Promise.all([
            api.get('/urls/', { signal }).catch(() => ({ data: { results: [] } })),
            api.get('/scans/list/', { signal }).catch(() => ({ data: { results: [] } })),
            api.get('/auth/organization/', { signal }).catch(() => ({ data: null })),
        ])
        // ... actualizar estado
    } catch (err) {
        if (err.code !== 'ERR_CANCELED') console.error(...)
    } finally {
        setLoading(false)
    }
}
```

Para funciones de carga reutilizadas (llamadas también por handlers de usuario como `loadData` en `URLs.jsx` y `loadData` en `AdminDashboard.jsx`), el parámetro `signal` es opcional con valor por defecto `undefined` para no romper los call sites existentes.

### Impacto

- **Antes:** Requests HTTP no cancelables; posibles race conditions y uso innecesario de ancho de banda/servidor.
- **Después:** Requests abortados al desmontar el componente; el error `ERR_CANCELED` se suprime correctamente en el catch.
